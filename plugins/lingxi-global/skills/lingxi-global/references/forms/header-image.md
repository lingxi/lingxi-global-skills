# Form Header Image: Upload and Replace

Read this workflow only when adding or replacing a header image; changing only display settings such as height does not require re-uploading. Check the config structure against live `get_form_definition_options(section=config,config_key=theme_config)`; for field explanations, see [form-theme-fields.md](form-theme-fields.md). The header image is not an upload question or the activity portal image.

1. Include the real image, display state and related settings in this round's business confirmation. Confirm that the current environment can read and transmit the file bytes: for a designed image, generate and preview it first; for an existing image, obtain a readable file. Do not use image IDs/paths/URLs from templates as source material. If the current environment cannot transmit file bytes, say so in this turn and let the user choose either to continue creating without a header image for now or to provide a readable image instead; do not wait until the upload fails to raise it.
2. Call `prepare_form_header_image_upload({original_name,size,mime_type})`. It only issues upload instructions; it **does not transmit the file**.
3. Within the validity period, transmit the real bytes strictly according to the returned `method/url/headers/form_fields`: for PUT, send the raw content; for POST, attach all form_fields and then attach file last, letting the client generate the multipart boundary. A 2xx with an empty response body can be a success; do not require JSON. Never disclose the signed URL.
4. After a successful upload, write `upload.upload_id` into `definition.config.theme_config.header_image.image.upload_id` when creating, or into `changes.config.theme_config.header_image.image.upload_id` when editing. Keep the confirmed height, position and display state. For a new form, validate (preflight) the final definition again; for an edit, save with the latest edit token.
5. After saving, read back the image reference, original file name, height, position and display state; after publishing, verify the live config separately. Verify the resource itself once the image is accessible; a config read-back is not a substitute for visual acceptance of the page.

Prepare, transmit and save are separate outcomes. If transmission or saving fails, tell the user which step it stopped at; do not treat a local path, an external URL or an untransmitted upload_id as uploaded. If it cannot be completed, do not switch to continuing without a header image on your own; instead let the user choose either to continue without a header image for now or to provide another image. The save service still checks organization ownership and the cloud object. Other draft images must use the trusted references they support; do not borrow the submission upload tool.
