# Create from the business plan and publish

Settle business facts, presets and execution scope per [business-brief.md](business-brief.md) first. This flow only turns the business definition into the actual result; to modify an existing form use [edit-and-publish.md](edit-and-publish.md). Consult [form-definition.md](form-definition.md) section by section for field explanations; do not copy it wholesale.

## Get the contract and assemble

1. Use `get_form_definition_options(section=basics)` to check abilities and languages. For questions, fetch the complete live templates for the question types involved with `section=item_types`; query one with `type_code` or several with `type_codes`, never both at once. Keep the necessary `source_type/category/rule_config/common_config/option`, add a unique `item_key` and `sort`, and strip `item_kind/ai_note`, answer examples and system questions. Hong Kong phone area codes must exist in the live `area_code.choices`.
2. Query config with `section=config,config_key=...` for the sections involved, and pass only accepted, supported nodes. The returned structure example is not the complete set of required rules, nor the actual defaults; consult the relevant field manual and validate when needed. For contact collection, set both `submitted_config.contact_collect_mode` and the question-level `common_config.collect_to_contact`; use `selected=ignore` to keep existing data and `replace` only when overwriting is authorized; when not collecting, explicitly turn both levels off. Leaving out the global policy may cause the designer to later auto-add name, mobile and email questions.
3. For a full activity, first query `get_form_definition_options(section=activity)`; you can query parts with `activity_section=activity` or `slots`. Build `ability=activity`, `activity:{activity:{...},slots:[...]}` from the returned fields, enums, conditions and templates, with at least one real, valid time slot. Distinguish actual defaults from examples; never use example dates and locations as user facts. For regions, query level by level with `list_areas(parent_id=0)` and the returned IDs; store street/venue text separately and never guess IDs. When the contract is missing or the required participation mode is not currently supported, state the capability gap; do not resort to reading PHP, and do not disguise it as some other config. Only when a basic draft is explicitly requested may you omit the whole `activity`, listing what remains to be filled in.
4. Set the source language explicitly with `source_language`; handle other languages per [translation.md](translation.md). Save the success page via the actual `notification_config.customized_feedback`. Upload the header image for real per [header-image.md](header-image.md). Free/paid intent is not payment config, and this definition has no standalone `pricing_mode`; payment questions and settings must go together. A notification setting being saveable does not mean it has run or is currently available; state the limits of unverified capabilities.
5. Check dates, time slots, registration period, location, quota, fees and contact details against the business definition, then call `validate_form_definition({definition})`. Fix all independent errors in `errors`, then re-validate the full definition; fix format problems yourself, but take changes in business meaning back to the user for confirmation; never delete user requirements to clear errors. After uploads finish, validate the final definition again.

Organization, creator, approval and publish status are controlled by the server. Validation does not prove venue availability, successful upload, effective payment or going live; activity dates and sessions also have save-time business validation.

## Save, verify fully and deliver

When the business batch is explicitly authorized and the scope is unchanged, execute directly; do not reconfirm before saving or before each tool. This part involves multiple writes and uploads; report progress in one sentence of business language, not tool by tool.

1. Call `create_form_draft({request_id,definition})` with a stable UUID and get `form_id/revision_no/status` synchronously. If the result is unclear, check first; retry with the original UUID only for the same user, the same organization and an identical definition. Changing the definition requires re-validating, rechecking authorization and a new UUID.
2. Call `get_form_draft(form_id)` and check it against the complete business definition: title, body, all ordinary questions, required/options/conditions, config, contact policy, header image, revision and approval status; for activities also check the dates, locations and settings in `activity_detail.activity/slots`. Never pass off request parameters as save results when read-back fields are missing. Fix mismatches at the draft stage and re-read; confirm business changes first; never publish until the check is consistent.
3. When other languages are chosen, handle translations after the source text is published: translation targets only the latest published version, and drafts cannot be translated. When only draft creation is authorized, keep a to-do "complete translations after the source text goes live" and tell the user; do not publish the source text on your own.
4. When stopping at draft, deliver the real saved status together with `edit_url`: it is the admin editor link, requires admin console login and is only for the authorized user to review personally; it is not the public form link and cannot be forwarded externally as a preview. Restate the actually saved title, questions and key settings as needed. An empty `edit_url` means the organization has no admin primary domain configured; say so plainly. When create and publish is authorized, read the current permissions per [publish.md](publish.md) and carry out the covered submit for approval and publish; while waiting for approval, explain the status, do not ask another round whether to continue, and do not claim it is live.
5. After publishing, verify the live content and the real `client_url`. When other languages are chosen, now read the translation workspace per the [translation flow](translation.md), complete the translations with the published revision number it returns, and fully check the source text, translations and success page; publishing the source text and completing translations are two separate steps — report a multilingual task as complete only after verifying translation completion. Internal verification does not mean reposting the full text to the user. On normal success, give the user one sentence saying it is done, plus the link. On failure, missing items or mismatches, explain what was completed and what is blocking, referring to the form by its title (give its ID only if the user asks), and continue from the original draft; never create a duplicate form.

For complex question type rehearsals, describe validation, saving, submit for approval / publish and manual steps according to the actual coverage; never call uncovered items verified.

## What the user sees

Keep the user oriented at every stage. Use their language; examples below are in Traditional Chinese.

| Stage | What you show |
| --- | --- |
| 1. Understand | Restate the goal in one sentence. List every missing essential in one message, each with a suggested default (「名額：不限（建議）」). |
| 2. Plan card | Before building, show one compact summary: title, who it is for, dates / time slots / venue (activities), the question list with required marks, fees and quota, notifications, and whether the organization requires approval. Ask the user to confirm or change it. |
| 3. Building | One progress line, e.g. 「正在建立草稿並核對內容……」. Do not narrate individual tools or fields. |
| 4. Result | 「✓ 已建立草稿」 plus a short check summary (what was saved matches the plan, or what differs), the admin editor link, and the current status in plain words — e.g. 「機構要求審核，下一步是提交審核」. |
| 5. Next steps | Offer one to three choices that fit the status and the user's permissions, e.g. 提交審核 / 直接發佈 / 先到後台預覽. |
| 6. Live | 「✓ 已發佈」 plus the public form link. If translations are in scope, say that completing them is the next step. |

If something fails or does not match, say what was saved, what is missing and what you will do next — refer to the form by its title, not its ID.
