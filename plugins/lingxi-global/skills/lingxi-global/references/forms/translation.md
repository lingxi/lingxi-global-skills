# Saving form translations

Use this only when the user chooses another language or a change affects existing translations. Once the source text is stable, read the actual `source_language`; do not use a translation operation to change the source language. Translation applies only to the latest published revision and is independent of the shared draft: publish an unpublished form first; unpublished changes in the draft do not enter the translations, so translate added or changed content after publishing.

1. Call `get_form_translation_workspace(form_id,target_language)` to get the published revision's `revision_no`, the actual units, the source text and `source_hash`; previewing does not require enabling the language first. Cover every applicable unit, including title, questions, options, config and the success page, and preserve variables and rich text.
2. Confirm the language scope, the impact once it takes effect, and whether the user delegates the translation. When the user has delegated translation, the agent checks it completely; showing every translation is not mandatory. When it is not delegated, or the user explicitly asks to review, show the translations for confirmation first. When an existing batch authorization already covers it and matches the workspace, reuse it; for additions or changes, confirm only the differences. Include already-enabled languages in the check. Do not enable a language the user has not accepted, and do not disable an existing language on your own. When showing translations to the user, do not expose internal field names, tool names, JSON or IDs unless the user asks.
3. Run `changes.translation` through separate `update_form_draft` calls, in this order:
   - `action=languages`: enable confirmed languages with `enabled_languages`; when a language must be disabled, submit only the authorized `disabled_languages`.
   - `action=save`: for each target language, pass `target_language` and `translations`; every entry uses the workspace's `unit_key/source_hash` and the checked `translated_text`.
   - Re-read the workspace for every enabled target language; after confirming that the source scope is unchanged and no translation is missing or stale, complete and publish the translation snapshot with a separate `action=complete`.
4. Pass only one translation operation per call, and never mix it with ordinary changes. For `expected_revision_no`, pass the published revision number returned by the workspace (not the draft revision number); for `expected_edit_token`, use the edit token from the latest `get_form_draft`, and re-read after each write to get the new token. If the form is republished in the meantime and the revision changes, re-read the workspace and compare again; if this affects already-confirmed content, get additional confirmation. On failure or an incomplete check, stop and explain; resume from the translations already saved.

For every selected language, internally check that the submit success page body matches the meaning of the actual result; showing it again is not required. `complete` does not publish the form; if the organization does not support multiple languages, explain the limitation. For payload constraints, see "Update and translation payloads" in [form-definition.md](form-definition.md).
