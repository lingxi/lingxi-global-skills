# Form creation JSON: index and boundaries

Creating a form does not require one big JSON with every setting: a minimal definition can contain only a title; add questions, settings and the activity schedule only as a complete form actually needs them. The field catalog is for the agent's internal assembly and explanation; business users are never asked to fill in JSON. At runtime, read `get_form_definition_options` on demand: use `section=basics/item_types/config` for basics, question types and config respectively, and `section=activity` for activities. The current MCP response is the contract; config structure examples are not the complete business rules, and this manual keeps their non-obvious semantics.

In every field table, the "Field prefix" plus the first column is the full path. For example, prefix `definition.config.submit_config` plus `frequency.not_allow_multiple_submissions.condition[]` gives an actual field five or more levels deep. `[]` denotes an array element and `*` a dynamic key. Shared structures list every applicable prefix; never attach a structure anywhere else at will.

"Saved" means a valid business value in the request; "candidate" means option metadata supplied by the options tool / edit API; "read back" means a display value generated by the server or file system; "reserved/difference" means you cannot promise execution based on it. Unless stated otherwise, an object is only a container for the fields below it, and an array only stores an ordered list of the corresponding elements.

## Create request and basics

Field prefix: `request`

| Field | Type / limits | Purpose |
| --- | --- | --- |
| `request_id` | UUID, required | Idempotency key for creation; a retry with the same key must use the same definition; never use it to create a different form. |
| `definition` | Object, required | Business definition; only the 9 root fields in the table below are allowed. |

Field prefix: `definition`

| Field | Type / limits | Purpose |
| --- | --- | --- |
| `title` | String, required, max 256 characters | Form/activity name. The question save chain has corresponding constraints too; the validate (preflight) result is authoritative. |
| `subtitle` | String, max 256 characters, optional | Registration page subtitle/summary; not the activity schedule. |
| `description` | String, optional | Page body text; may contain rich text the current product supports; never include false facts. |
| `source_language` | Current language code, optional | Source text language; query the currently supported candidates via `basics`. Target languages go through the translation operation separately. |
| `category_id` | Integer >= 0, optional | Form category ID; 0 means unspecified; a non-zero value must be a real candidate of the current organization. |
| `ability` | `form` / `activity`, default `form` | Ordinary form or activity; must be `activity` when submitting a full activity object. |
| `items` | List, 1..500 items when provided | Ordinary questions and layout questions; see the question type manual. System questions are generated by the server. |
| `config` | Object, optional | The 10 config sections in the table below; pass only confirmed, supported settings. |
| `activity` | Object, optional | `{activity: {...}, slots: [...]}`; the second-level `activity` is not a duplication mistake. Full rules are in the activity manual. |

Field prefix: `definition.config`

| Field | Type | Purpose |
| --- | --- | --- |
| `common_config` | Object | Participation policy, management permissions, user agreement and terms of service. |
| `submit_config` | Object | Open period, quota, repeat submissions, password, numbering, and allow/block lists. |
| `submitted_config` | Object | Contact collection, special numbering, categories and tags. |
| `notification_config` | Object | Submission messages, success page feedback and promotion entry points. |
| `automation_config` | Object | Submission approval and approval notifications; not the form's go-live approval. |
| `jump_logic_config` | Object | Show later questions based on choice question answers. |
| `share_config` | Object | Portal display, channels, social sharing, web embedding. |
| `ext_config` | Object | WeChat and other extension settings. |
| `payment_config` | Object | Discounts, stock, electronic receipts and payment methods. |
| `theme_config` | Object | Visual config of the form page. |

Organization, creator, permission decisions, draft revision, and the form's approval/publish status are controlled by the server; do not add them to `definition`. `valid=true` only proves static definition validation passed; saving also runs permission, resource ownership, business rule and upload reference checks.

## Types and update semantics

- `Y/N` is an integer: `1=yes/enabled`, `2=no/disabled`, not a boolean. The config Schema also accepts strings `"1"/"2"`, but the integer rules for questions and activities are stricter, so always use integers. `hidden=1` means hidden; `private=1` means a private question; never invert their meaning.
- In the config Schema, `scalar` only requires a non-object/non-array value and accepts a scalar or null; the business types and values listed in the manuals must still pass business validation. A field being optional, or structurally allowing null, does not mean required content can be missing when the feature is enabled.
- Examples are not actual defaults. Creation defaults and edit-state backfill are decided by `FormConfigDefaultService`; different abilities, organization resources and edit states change the returned values. Activity portal defaults differ from ordinary forms; never copy one example and submit it in full.
- `config` updates merge by each section's direct child keys — **not an unlimited recursive merge**. For example, submitting `submit_config.frequency` replaces the whole `frequency`; submitting `common_config.permissions` must keep the whole permissions object. Read the latest config first and build the complete affected child object. An explicit null clears; only omission means no change; specific nodes may also be normalized by business logic. For the header image, objects inside `theme_config.header_image.image` are preserved recursively key by key, lists (including `[]`) are replaced as a whole, and `image:null` clears the image; changing only `height.default` keeps the height candidates, original image and position. The WeChat section has its own partial-merge handling; do not generalize these special cases to all sections.
- Config depth limit is 15; each section has at most 5000 nodes, objects at most 200 keys, a single string at most 100000 bytes, and cumulative strings per section at most 1000000 bytes; arrays also have the limits noted in each table, and at most 500 items when not specified. An open object only means the structure allows unknown keys, not that unknown keys do anything.
- Uploads use the real `upload_id` from an actual upload; saving verifies organization ownership and resolves the trusted file. The `id` of an existing file must also pass the ownership check. `path/url/original_name` are display information; never substitute a local path or an arbitrary URL for an upload.

## Update and translation payloads

Field prefix: `update request`

| Field | Type / limits | Purpose |
| --- | --- | --- |
| `form_id` | Real ID required by the tool | Form being modified. |
| `expected_edit_token` | `form.edit_token` returned by the latest `get_form_draft` | Use the current edit token for every save; required when there is no draft; never substitute the last modifier or the draft revision number. |
| `expected_revision_no` | Optional; ≥1 when provided | For ordinary edits, the latest draft revision number — a revision check kept for compatibility with older calls; saves within the same draft do not necessarily change the revision number, so it cannot by itself prevent concurrent overwrites; omit it when there is no draft. For translation operations, the published revision number returned by the translation workspace. |
| `changes` | Object | Allows `title/subtitle/description/items/config/activity`, or a single standalone `translation`. |

`changes.items` is the complete list of ordinary questions; when changing only the title, subtitle or body, do not pass `items` — the server keeps the existing questions. `changes.activity` is the complete activity save payload. `changes.config` follows the merge rules above. `ability/category_id/source_language` are not editable keys in this update API.

When there is no draft, an ordinary content update uses the edit token to verify the current state and follows the admin console's flow for creating a shared draft; translation operations neither depend on nor change the draft, and apply to the latest published version. If a draft exists, keep editing that draft. `saved_to=draft` and `status=draft` in the response indicate the save target of this call; `form_status` indicates the form's actual status. Saving a draft for a published form neither takes it offline nor publishes this change. Re-read after saving to get the new `edit_token`. Submit for approval and publish are still separate tools that carry the latest draft revision number and edit token; handle differences and authorization per [edit-and-publish.md](edit-and-publish.md).

Field prefix: `changes.translation`

| Field | Type / limits | Purpose |
| --- | --- | --- |
| `action` | `languages` / `save` / `complete` | Enable languages, save translations, or complete the translation snapshot; never mix with ordinary edits. |
| `enabled_languages` | List of language codes, max 2 | Required for `languages`; the current set of target languages. |
| `disabled_languages` | List of language codes, max 2, optional | Languages to disable explicitly; must not also appear in the enabled list. |
| `target_language` | Supported language code | Target language for `save`. |
| `translations` | List, 1..2000 | Translation units saved in this call. |
| `translations[].unit_key` | 32 characters, no duplicates | Translation unit identifier returned by the workspace. |
| `translations[].source_hash` | 32 characters | Workspace source text hash; prevents saving stale translations. |
| `translations[].translated_text` | String or null, max 1000000 characters | Translation body; preserve variables and rich text. |

`complete` passes only action; completing the translation snapshot does not publish the form. For confirmation and execution order see [translation.md](translation.md).

## Sources and maintenance

When MCP does not provide enough of a contract, state the capability gap; do not read source code or bypass MCP to execute.

Read-back APIs do not necessarily include the full activity schedule; never describe missing nodes as "verified by read-back".
