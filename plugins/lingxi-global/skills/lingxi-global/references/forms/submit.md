# LingXi MCP: submit on behalf (admin submission)

This flow is an admin submission on behalf of someone. Confirm the required tools are available as you work through the steps below; connection, authorization and access path follow the Skill entry point.

These tools create **admin submissions on behalf of someone**, not visitor submissions through the public form page. They bypass the public side's time window, password, allow/block lists, repeat-submission, user agreement acceptance and quota limits, but question types, conditions, question groups, payment tiers and so on are still validated. A submission may sync contacts, create activity registrations, send notifications, or create records pending approval / pending payment. If the user wants to verify the public side's participation limits or submit as a visitor, do not use this flow as a substitute; explain the difference first and clarify the goal.

## Read and ask

For forms with many questions, first call `get_form_submission_schema(form_id,view=summary)` to get the complete question list, `submission_effects` and `schema_hash`, then follow the returned `pagination` and call `view=page,page=...,page_size=...` page by page to get the complete rules and options of every question that actually needs an answer; each page's `schema_hash` must match the list's — if it changes mid-read, read again. Never miss middle questions because a single output was truncated. The default `full` is for small forms or compatibility with older clients. When reading the revision again, check summary first; if `schema_hash` has changed, re-read the complete questions and rules.

For batch demos, first list a coverage matrix per person: keep "fill every answerable question" separate from "required plus a sample", and state which sensitive information, uploads or signatures lack real material and are therefore not covered. Record, per submission, progress through validation, submission, submission result and per-question read-back; never count unanswered question types as full-question verification.

1. When the user gives a numeric form ID, read it with the summary/page flow above; when they give only a title or a public link, first use `list_forms` to locate it in the currently authorized organization and check the title and link. If there are multiple candidates, ask the user to choose; never guess the encrypted ID in the link as a numeric ID. The structure read must succeed with `form.status=published`; record the returned `form.id`, `revision_no`, questions and config. Reading needs only view permission; the later validation, upload and submission also need edit permission.
2. From `items`' `item_key`, `type_code`, `group_code`, `rule_config`, `common_config`, `option` and the form's jump logic config, identify the required questions, options and formats that are actually visible and currently applicable. Exclude descriptions, dividers, page breaks, system questions and hidden questions; ask first the questions that affect conditional display, then follow up with the questions those conditions trigger and each answer for repeated question groups. Ask in natural language, in batches; never put JSON or field keys to the user as questions. Do not ask again about optional questions the user has explicitly declined.
3. Inside each answer use `item_key` as the key and keep the structure the API requires; never turn name, mobile, address, choice, date, question group or upload answers into plain text on your own. `answer_shape_example` only hints at the shape; it does not represent available options or valid test values; options and limits follow the current question config. Check mobile numbers' area code and length against `mobile_area_rules`; for addresses, first use `list_areas(parent_id=0)` to look up real options level by level, and put the localized **names** of province/city/district in the answer, not area IDs; organize repeated question groups by the configured count with keys such as `子题item_key-2` (the sub-question's item_key followed by `-2`). Never invent missing personal data on the user's behalf.
4. Call `prepare_form_submission_upload` for file, image or signature questions only when the user has provided the actual file and this environment can transfer the bytes. Check revision, question key, extension, MIME type, size and count; upload the real file bytes directly, strictly per the returned `method`, `url`, `headers`, `form_fields`; after success, put the returned `answer` (shaped like `[{"upload_id":"..."}]`) into the answers. Never draw a signature on the user's behalf; never leak the signature URL to anyone else, and never treat a local path, external URL, file ID, or an `upload_id` whose bytes have not been transferred as an uploaded answer. If a required file cannot be uploaded, stop and explain.

## Validate, correct and submit

1. After collecting all **currently applicable** required questions (plus any optional questions the user is willing to answer), call `validate_form_answers({form_id,revision_no,answers})`; `answers` must not be empty. Validation does not create a submission. When `valid=false`, map the field paths in `errors` to questions the user can understand, keep the other answers, and ask the user to fix only the affected questions; when conditions change, recheck newly required questions, then re-validate with the corrected full answer set until `valid=true`. Never hide errors by deleting answers the user wants to submit.
2. After validation passes, read `get_form_submission_schema(form_id,view=summary)` once more. If the form is no longer published, or `revision_no` or `schema_hash` has changed, re-read the complete questions and rules, collect the affected answers and re-validate; never submit directly against an old revision. Prepare and submit a separate submission for each person you submit on behalf of, unless the form is explicitly designed with a repeated participant question group within one submission.
3. Show the user the form for this submission, the person being submitted on behalf of, the final answer to each question (for sensitive information show only the fragment needed for checking), skipped optional questions, and any possible contact, registration, notification, approval or payment effects; state clearly that this is a **real admin submission on behalf of someone**. Proceed to step 4 only after the user has seen this final summary and explicitly agreed to submit. The user's initial "fill it in / submit it for me" is not final consent after review.
4. After final confirmation, generate a separate stable UUID `request_id` for each person, and pass it to `submit_form_answers` together with exactly the same `form_id`, `revision_no` and `answers` as the latest successful validation; if the answers or revision change, re-validate, reconfirm and use a new UUID. After receiving the result, use `get_form_submission_result(form_id,request_id,include_answers=true)` to check the current status and the answer actually saved for each question; for sensitive information, check only what is necessary within the authorized scope. `pending_approval` and `pending_payment` are not completion, and the submission status does not prove the asynchronous contact and notification side effects either. On timeout or an unclear result, first **look up the submission result read-only** with the same UUID; never automatically resubmit on `pending_unknown` or `created_response_unknown`. Idempotency protection for the same UUID and the same payload does not permit changing business intent or bypassing final confirmation; not finding a submission result does not mean it was definitely not submitted. If it stays uncertain, tell the user the last known status in plain words and that it needs checking; keep the form ID and the original request ID, and give them to the user only if they ask or need them to follow up with support. Do not promise automatic retry. Check older submissions with `list_form_submissions` and `get_form_submission` per the [submission history query flow](query-submissions.md); they do not replace checking the result of an uncertain submission by `request_id`.
